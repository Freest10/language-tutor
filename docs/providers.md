# Провайдеры: LLM, распознавание и синтез речи

Приложение не содержит моделей. Все три ИИ-функции ходят по **OpenAI-совместимому HTTP**,
поэтому провайдер меняется переменными в `.env` — без единой правки кода.

| Функция                  | Куда ходит приложение                      | Переменные                                                                            |
| ------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------- |
| Языковая модель          | `POST {LLM_BASE_URL}/chat/completions`     | `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_TIMEOUT_MS`, `LLM_TEMPERATURE`       |
| Распознавание речи (STT) | `POST {STT_BASE_URL}/audio/transcriptions` | `STT_PROVIDER`, `STT_BASE_URL`, `STT_MODEL`, `STT_API_KEY`                            |
| Синтез речи (TTS)        | `POST {TTS_BASE_URL}/audio/speech`         | `TTS_PROVIDER`, `TTS_BASE_URL`, `TTS_MODEL`, `TTS_API_KEY`, `TTS_VOICE`, `TTS_FORMAT` |

`STT_PROVIDER` и `TTS_PROVIDER` принимают два значения:

- **`browser`** (по умолчанию) — работу делает браузер через Web Speech API. Серверные
  эндпоинты `/api/voice/stt` и `/api/voice/tts` при этом осознанно отвечают **501** с
  `details.reason = 'stt_browser_only'` / `'tts_browser_only'`. Это не ошибка, а сигнал
  фронту: «делай сам».
- **`openai`** — работу делает сервер, обращаясь к указанному эндпоинту.

## Три рабочих конфигурации

Готовые к копированию блоки лежат в `.env.example`; здесь — чем каждая платит.

### 1. Браузерный голос + локальная LLM (по умолчанию)

Поднимать нужно только модель. Голос обрабатывает браузер, тексты никуда не уходят.

```
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen3:8b
STT_PROVIDER=browser
TTS_PROVIDER=browser
```

**Цена выбора:** требуется браузер на Chromium (см. ниже про Firefox); качество
распознавания и голоса — какое даёт операционная система, оно заметно хуже whisper.

### 2. Полностью локальный стек в Docker

Голос тоже не покидает машину. Три профиля поднимаются независимо:

```
docker compose --profile ollama up -d    # LLM,           :11434
docker compose --profile stt up -d       # распознавание, :8000
docker compose --profile tts up -d       # синтез,        :8880
docker compose exec ollama ollama pull qwen3:8b
```

или `npm run stack:up` / `npm run stack:down`.

**Цена выбора:** несколько гигабайт образов и весов, заметная нагрузка на процессор.
**Ограничение Kokoro:** голоса есть не для всех языков — немецкого и русского среди них
нет. Для этих языков держите `TTS_PROVIDER=browser`, а серверным оставляйте только
распознавание.

### 3. Облачный OpenAI-совместимый провайдер

```
LLM_BASE_URL=https://api.openai.com/v1
STT_PROVIDER=openai
TTS_PROVIDER=openai
```

Для другого облака (OpenRouter, Groq, Together) меняется только `*_BASE_URL`.

**Цена выбора:** качество выше и ничего поднимать не надо, но **весь звук и все тексты
уроков уходят провайдеру**, а занятия стоят денег.

## Что нужно знать до того, как что-то не заработает

**Web Speech API фактически отсутствует в Firefox.** Формулировка «работает из коробки
без установки» означает браузер на Chromium. В Firefox приложение определит отсутствие API
и покажет, что делать, — но микрофон там не заработает, пока вы не включите серверное
распознавание (`STT_PROVIDER=openai`). Молча неработающей кнопки не будет.

**`GET /api/config` сообщает конфигурацию, а не живую доступность.** Провайдеры не
пингуются: такой пинг стоил бы дороже всего остального ответа. Поэтому «доступен» там
означает «настроен». Живую проверку делает `npm run smoke` — он реально дёргает модель.

**Модель меньше 8B заметно портит результат.** Форму ответа держит сам сервер модели:
приложение просит `response_format: json_schema`, и llama.cpp, Ollama, vLLM и OpenAI
генерируют строго по схеме — ответ не по схеме на них попросту невозможен. Сервер, который
такого режима не знает, получает `json_object`, а потом и обычный запрос: откат молчаливый,
настраивать его не нужно. Но схема держит только форму, а не смысл: на маленькой модели
шаги урока и проверка ответов остаются бедными, даже когда JSON безупречен.

**Имя модели в `LLM_MODEL` должно совпадать с установленной.** Ollama отвечает 404 на
модель, которой у неё нет, и приложение называет её прямо: «Модель «…» не найдена
у провайдера». Что установлено, покажет `ollama list`, поставить — `ollama pull <модель>`.

**Окно контекста у Ollama по умолчанию — 4096 токенов, и этого мало.** В промпт урока
уходят системная инструкция тьютора, план, сводка профиля, история занятий, цитаты
материалов и последние реплики диалога. Каждая из этих частей ограничена сервером по
символам, но в сумме они не помещаются в 4096 токенов, а llama.cpp при переполнении молча
срезает **начало** промпта — то есть правила тьютора. Поднимите окно у сервера модели:
`OLLAMA_CONTEXT_LENGTH=8192` (в `docker-compose.yml` профиля `ollama` уже задано) или
`num_ctx` в Modelfile. Признак проблемы: тьютор перестаёт держаться плана и начинает
отвечать на языке объяснений. Если в окно не помещается уже сам ответ, приложение говорит
об этом отдельно («модель оборвала ответ на полуслове») и не предлагает повторить запрос:
повтор оборвётся там же.

**Первый запрос к локальной модели долгий.** Веса грузятся в память; `LLM_TIMEOUT_MS` по
умолчанию 120 000 мс именно поэтому. В интерфейсе это закрыто индикатором «тьютор думает»
и блокировкой повторной отправки.

**Ответы не стримятся.** На локальной 8B-модели пауза между репликами — 5–20 секунд.

## Как проверить, что провайдер жив

```
npm run smoke
```

Скрипт последовательно проверяет живость сервера, конфигурацию, короткий запрос к модели,
доступность STT и TTS (если они не браузерные), чтение и запись профиля, создание материала,
генерацию плана урока и сводку прогресса. Каждый провал сопровождается строками «→» с
конкретным действием. Код возврата ненулевой, если хоть одна проверка провалилась.

Smoke **создаёт данные** (профиль, материал, урок). Чтобы не засорять рабочую базу,
запускайте сервер с отдельной: `DB_PATH=./data/smoke.db npm run dev:server`.

Точечно, вручную:

```
curl -s localhost:8787/api/health
curl -s localhost:8787/api/config
curl -s http://localhost:11434/v1/models          # жива ли LLM
curl -s http://localhost:8000/v1/models           # жив ли STT
curl -s http://localhost:8880/v1/audio/voices     # голоса TTS
```

## Как читать ошибки провайдера

Конверт ответа всегда `{ "error": { "code", "message", "details" } }`.

| Код                    | HTTP | Что случилось                                                              |
| ---------------------- | ---- | -------------------------------------------------------------------------- |
| `not_configured`       | 501  | провайдер выключен (`*_PROVIDER=browser`) или не заданы его адрес и модель |
| `upstream_unavailable` | 503  | не достучались: нет соединения или таймаут                                 |
| `upstream_error`       | 502  | провайдер ответил ошибкой либо вернул ответ не по схеме                    |

В `details.reason` лежит машиночитаемое уточнение: `llm_not_configured`, `llm_timeout`,
`llm_invalid_response`, `stt_browser_only` и так далее.
