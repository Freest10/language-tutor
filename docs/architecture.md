# Архитектура

Документ для того, кто будет дорабатывать приложение: как разложены пакеты, как данные
доходят от профиля до реплики тьютора и куда класть новое. Обоснования конкретных решений
лежат в JSDoc самих модулей — здесь только карта и правила, которые нельзя вывести из одного
файла. Про выбор провайдеров и их настройку — [providers.md](providers.md).

## Три воркспейса

Монорепо npm workspaces, зависимости идут строго в одну сторону: `shared` → `server`,
`shared` → `web`. Сервер и веб друг о друге не знают ничего, кроме контракта.

- **`shared` (`@lt/shared`)** — контракты. `shared/src/domain/` — доменные сущности и
  перечисления (языки, уровни CEFR, материалы, урок, задания, прогресс), `shared/src/api/` —
  DTO запросов и ответов каждого эндпоинта. Всё это zod-схемы, а типы выводятся из них.
- **`server` (`@lt/server`)** — Fastify поверх SQLite. `routes/` тонкие: разбор запроса,
  вызов сервиса, ответ. Прикладная логика — в `services/`, SQL — только в `repositories/`,
  доступ к базе и мапперы row ↔ домен — в `db/`, HTTP к моделям — в `providers/`,
  сборка промптов и схемы ответов модели — в `prompts/`.
- **`web` (`@lt/web`)** — React и Vite. `api/` — клиент HTTP, `features/<фича>/` — хуки
  и компоненты фичи, `pages/` — экраны, `i18n/` — переводы, `context/` — возможности сервера
  из `GET /api/config`.

**Почему контракты вынесены отдельно.** Одна и та же схема проверяет тело запроса на сервере,
сериализует ответ (`schema.response` у Fastify) и даёт типы клиенту, так что ломающее изменение
DTO валит сборку обеих сторон сразу, а не всплывает в рантайме на живом уроке. Пакеты
разрабатывались параллельно поверх зафиксированного контракта, и это же свойство делает
безопасным дальнейшее расширение: правка `shared` немедленно показывает всех, кого она задела.

Практическое следствие: `server` импортирует собранный `shared/dist`, поэтому `npm run dev`,
`npm test` и `npm run typecheck` сначала собирают `shared`. Вебу пересборка не нужна —
`web/vite.config.ts` алиасит `@lt/shared` на исходники ради HMR.

## Поток данных урока

Создание урока (`POST /api/lessons`, `services/lessonPlanService.ts`):

1. Сервер собирает контекст сам, а не поручает это модели: сводка профиля
   (`profileService.getProfileForPrompt()`), накопленная история занятий
   (`services/learnerContext.ts`: уровень, цели, интересы, объём практики, частые категории
   ошибок, последние исправления, слова в работе, темы уроков) и фрагменты выбранных
   материалов (`materialService.getChunksForLesson()` — отбор по ключевым словам под бюджет
   символов, без эмбеддингов).
2. `prompts/lessonPlan.ts` превращает это в сообщения для модели и объявляет zod-схему ответа.
3. `providers/structuredJson.ts` добивается JSON по схеме: `response_format: json_object`
   с молчаливым откатом, если сервер модели его не знает, извлечение JSON из текста и один
   ремонтный заход с перечнем претензий Zod. Не вышло — `ProviderError`, который маршрут
   переводит в 502.
4. Сервер правит то, что модель делает плохо: число шагов держится схемой (4–7), сумма минут
   при отклонении больше ±20% масштабируется пропорционально.
5. План пишется одной транзакцией в `lessons`, `lesson_plan_steps` и `lesson_materials`:
   урок без шагов хуже, чем отсутствие урока.
6. Ответ уходит по `createLessonResponseSchema`, и по нему же рисуются экраны
   `web/src/features/lessons/` и `web/src/pages/LessonPlanPage.tsx`.

Ход урока (`POST /api/lessons/:id/turns`, `services/lessonSessionService.ts`) идёт по тому же
маршруту, но с двумя отличиями. Первое: реплика ученика сохраняется **до** обращения к модели —
на локальной модели отказы регулярны, и сказанное учеником терять нельзя. Второе: всё
остальное — ответ тьютора, исправления, сгенерированные задания, статус шага, записи словаря
и журнала ошибок — пишется одной транзакцией уже после успешного ответа. Завершение урока
(`/complete`) добавляет сводку и пересчёт уровня.

Отдельного эндпоинта у заданий нет: они рождаются внутри хода урока и при переходе на новый шаг
и приезжают клиенту полем `exercises[]`.

## Один контракт на три ИИ-функции

Языковая модель, распознавание и синтез речи ходят по OpenAI-совместимому HTTP:
`/v1/chat/completions`, `/v1/audio/transcriptions`, `/v1/audio/speech`. Весь сетевой код лежит
в `providers/openaiCompatible.ts`, готовность провайдера считает `providers/factory.ts` — тем же
предикатом, которым отвечает `GET /api/config`, иначе конфигурация обещала бы возможность,
которая потом отвечает 501.

Что это даёт: смена Ollama на LM Studio или на облачный ключ — это правка `.env`, а не кода;
тесты подменяют ровно один слой; браузерный режим голоса — это просто «сервер не участвует»
(501 с `details.reason = 'stt_browser_only'` / `'tts_browser_only'`, фронт читает это как
«делай сам»). Цена — общий знаменатель возможностей: ничего специфичного для конкретного
провайдера в коде нет.

## Схема базы

SQLite через `better-sqlite3`, одно соединение на процесс (`db/connection.ts`, режим WAL,
`foreign_keys = ON`). Миграции — нумерованные файлы `NNN_name.sql` в
`server/src/db/migrations/`, применяются по возрастанию версии в транзакции, версия хранится
в `PRAGMA user_version` (`db/migrate.ts`). Прогон идемпотентен и запускается сам при первом
обращении к базе; вручную — `npm run db:migrate`. Новая миграция — это новый файл рядом,
`001_init.sql` не редактируется.

Четырнадцать таблиц из `001_init.sql`:

- `profile` — ровно одна строка с `id = '1'`: приложение однопользовательское, строка создаётся
  миграцией, а признак незавершённого онбординга — колонка `onboarding_completed`;
- `materials` и `material_chunks` — материал и его фрагменты; неудача извлечения текста
  хранится машиночитаемым статусом `error_*`, а не пропавшей записью;
- `placement_sessions` и `placement_turns` — сессия определения уровня, её вопросы, ответы
  и оценки;
- `lessons`, `lesson_plan_steps`, `lesson_materials` — урок, шаги плана и связь с материалами;
- `lesson_messages` — реплики диалога урока; `audio_path` зарезервирована и всегда `NULL`;
- `exercises` и `exercise_attempts` — задания и попытки с оценкой и исправлениями;
- `vocabulary_items` — личный словарь, дедупликация по паре «язык + лемма»;
- `error_log` — журнал ошибок по категориям, записи неизменяемы;
- `level_history` — история уровня: обоснование и метрики обязательны для каждой записи.

Соглашения схемы описаны в шапке миграции: идентификаторы — TEXT с UUID, даты — TEXT ISO-8601
в UTC (строковая сортировка совпадает с хронологической), массивы и объекты — JSON в TEXT,
булевы — 0/1, а CHECK-ограничения дословно повторяют перечисления из `@lt/shared`, чтобы
расхождение схемы и контракта падало на вставке, а не у клиента. Ссылки на урок, шаг и задание
в словаре и журнале ошибок гасятся в `NULL`: статистика переживает удаление источника.

## Голосовой цикл

Запись → расшифровка → правка текста → ход урока → озвучивание.

Вся клиентская часть — в `web/src/features/voice/`: `useVoiceInput` выбирает путь по
`GET /api/config` (браузерный `useSpeechRecognition` поверх Web Speech API либо запись
`useMicRecorder` и `POST /api/voice/stt`), `useTextToSpeech` — озвучивание,
`PushToTalkButton` и `VoiceStatus` — кнопка и состояние. Отсутствие возможности — это не
молчащая кнопка, а явный отказ с подсказкой.

**Почему расшифровка правится до отправки.** Распознавание ошибается, а реплика ученика уходит
и в промпт, и в историю урока, и в разбор ошибок: исправлять «ошибку», которой ученик не делал,
хуже, чем потратить секунду на правку. Поэтому расшифровка попадает в поле ввода
(`features/lessonRoom/MessageComposer.tsx` и `ExercisePanel.tsx`), а отправляет её ученик.
Пометка `source: 'voice'` и длительность записи при этом сохраняются — серверу важно знать,
что реплика была надиктована.

Само аудио никуда не сохраняется: запись живёт до ответа распознавателя. Синтез отдаёт JSON
с `audioBase64`, а не бинарный поток, — ошибки приходят тем же конвертом `{ error }`, что и
у остальных эндпоинтов.

## Бюджеты промптов

Окно контекста локальной модели невелико (у Ollama по умолчанию 4096 токенов), а llama.cpp
при переполнении срезает **начало** промпта — то есть системную инструкцию тьютора. Урок при
этом не падает, он тихо разъезжается: тьютор перестаёт держаться плана. Поэтому у каждой части
промпта есть предел в символах:

- `LEARNER_CONTEXT_MAX_CHARS` = 1200 — блок «что известно об ученике»
  (`services/learnerContext.ts`); строки идут по убыванию важности, первая непоместившаяся
  обрывает сборку;
- `TUTOR_HISTORY_WINDOW` = 12 реплик и `TUTOR_RECENT_MAX_CHARS` = 6000 — окно диалога;
  что было раньше, сжимается в сводку не длиннее `TUTOR_DIGEST_MAX_CHARS` = 600
  (`prompts/tutorTurn.ts`);
- `TUTOR_MATERIAL_BUDGET_CHARS` = 2500 и `TUTOR_MATERIAL_MAX_CHUNKS` = 4 — цитаты материалов
  в ходе урока;
- `LESSON_MATERIAL_BUDGET_CHARS` = 6000 и `LESSON_MATERIAL_MAX_CHUNKS` = 12 — цитаты
  в планировщике (`prompts/lessonPlan.ts`): там нет истории диалога, и места больше.

Ограничивать нужно и число элементов, и символы: двенадцать реплик по 4000 символов (предел
контракта) переполнят окно ничуть не хуже, чем сотня коротких. Правило для доработок: добавляя
данные в промпт, добавляйте рядом и предел.

Недоверенный текст — цитаты материалов и реплики ученика — уходит в промпт в именованных
ограничителях `untrustedBlock()` из `prompts/format.ts`: он данные, а не инструкции модели.

## Автокоррекция уровня

Единственный источник порогов — `LEVEL_CHANGE_POLICY` в `shared/src/domain/progress.ts`:
не раньше трёх завершённых уроков, окно в три урока, повышение при точности выше 85%,
понижение ниже 50%, пауза в три урока между изменениями и не больше одной ступени CEFR за раз.
Сервер считает по этим значениям, клиент по ним же объясняет решение — дублировать пороги
нельзя ни в UI, ни в промптах.

Решение принимает чистая функция `decideLevelChange()` в `services/progressService.ts`
(её можно прогнать на синтетических данных, не поднимая базу), вызывается она на завершении
урока, когда урок уже помечен завершённым и попал в окно статистики. Запись в `level_history`
собирает общий `services/levelHistory.ts` — он одинаков для всех трёх источников изменения
уровня (`placement`, `progress`, `manual`), поэтому правило «первая запись истории — первичная
установка» живёт в одном месте. Тексты обоснований сервер пишет по-русски и хранит как есть.

## Куда добавлять новый язык изучения

1. `KNOWN_LANGUAGE_CODES` и `LANGUAGE_LABELS` в `shared/src/domain/language.ts` — код и
   названия. Дальше язык подхватывается сам: сервер принимает только коды из этого списка
   (`server/src/lib/languages.ts`), `GET /api/config` отдаёт его клиенту, форма профиля рисует
   по нему выпадающие списки, промпты подставляют название через `languageForPrompt()`.
2. Голос. Браузерный синтез возьмёт голос операционной системы; для серверного проверьте,
   что у провайдера вообще есть голос для этого языка (у Kokoro нет немецкого и русского),
   и задайте `TTS_VOICE`.
3. Проверьте распознавание: у whisper-моделей качество по языкам разное, и мелкая модель
   на редком языке может оказаться бесполезной.

Язык интерфейса — отдельная история и отдельная работа: `UI_LOCALES` в `web/src/i18n/index.ts`
плюс полный набор файлов `web/src/i18n/locales/<код>/<namespace>.json` по всем namespace
из `APP_NAMESPACES`. Изучаемый язык этого не требует.

## Куда добавлять новый тип задания

1. `EXERCISE_TYPES` в `shared/src/domain/exercise.ts` — контракт; при необходимости уточните
   поля `options`, `expectedAnswer` и `acceptableAnswers`.
2. Новая миграция: CHECK у `exercises.type` перечисляет значения явно, а SQLite не умеет менять
   ограничение на месте — таблицу придётся пересоздать.
3. `EXERCISE_TYPES_BY_STEP` в `server/src/prompts/exercise.ts` — на каких шагах плана новый вид
   уместен, плюс описание его формата в самом промпте.
4. Нормализация ответа модели в `server/src/services/exerciseService.ts`: сервер не доверяет
   модели форму задания (варианты остаются только у `multiple_choice`, у свободной речи нет
   эталонного ответа). Проверку ответа делает модель, а не сравнение строк, — если новый вид
   требует иного разбора, его место в `prompts/answerCheck.ts`.
5. UI ответа в `web/src/features/lessonRoom/ExercisePanel.tsx` и подписи в
   `web/src/i18n/locales/*/lessonRoom.json` (все языки интерфейса сразу).

## Проверки

Тесты лежат в `server/test/` и `web/test/` и гоняются через Vitest: `npm test`,
`npm run test:coverage`. Типы проверяются отдельно (`npm run typecheck`), правила —
`npm run lint`, форматирование — `npm run format:check`. Ни один из них не обращается
к живым моделям: провайдеры подменяются. Живой стек проверяет `npm run smoke` — он реально
дёргает модель, распознавание, синтез и проходит сценарий до плана урока, поэтому запускать его
лучше на отдельной базе: `DB_PATH=./data/smoke.db npm run dev:server`.
